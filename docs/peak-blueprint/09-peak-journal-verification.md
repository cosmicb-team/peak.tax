# 09 — ผลตรวจ journal จริงจาก PEAK (กิจการจำลอง, 9 พ.ย. 2569)

สร้างเอกสารทดสอบ → Approve → อ่าน journal → อ่าน Trial Balance → Void
ทุกรายการด้านล่างคือ **Observed** จาก PEAK จริง ไม่ใช่การอนุมาน

## 0. ข้อจำกัดของกิจการจำลองนี้
- รอบแรกกิจการ **ไม่ได้จด VAT** → PEAK ปฏิเสธ `isTaxInvoice=1` และ `vatType=3` (resCode 100 "Merchant is not registered for VAT") → รอบ 2 ทดสอบ VAT แล้ว (ดู §4)
- เอกสารที่มีการชำระแล้ว (DR, DP) void ไม่ได้จนกว่าจะยกเลิกการชำระก่อน
- GR ยังไม่ได้อนุมัติในการทดสอบ จึงไม่เห็น journal ของ GR

## 2. Trial balance ยืนยัน
- ก่อน void: Σ change Dr = Cr = 71,000 ; Σ ending = 46,300 สมดุล ✅
- หลัง void IV-B, RE, EXP×3, IR, GR, BN: บัญชีที่ถูก void **หายจาก TB ทั้งแถว** (ไม่ใช่กลับรายการ) — journal ถูกตั้ง `isVoid=1` และไม่ถูกนับ ✅ → ระบบเราทำแบบเดียวกันได้ (soft-void + exclude) หรือกลับรายการก็ได้ แต่ต้องเลือกแบบเดียว
- หลัง void เอกสารที่มี payment (IV-B) PEAK void การชำระให้อัตโนมัติ; `GetInvoice` ของเอกสาร void คืน `status: "Draft"`, `journals: []`, `paidPayments: []` (ไม่มี field isVoid ใน invoice get) ⚠️

## 3. กฎที่ค้นพบ (ต้องเข้าระบบเรา)

### 3.1 โครง journal ต่อเอกสาร
| เหตุการณ์ | จำนวน journal | เล่ม |
|---|---|---|
| IV / EXP Approve ไม่มีชำระ | 1 | SV / UV |
| IV Approve + ชำระพร้อมกัน | **2** | SV (รับรู้รายได้+ลูกหนี้) แล้ว RV (รับเงิน ตัดลูกหนี้) |
| EXP Approve + ชำระพร้อมกัน | **1** | PV รวม (ค่าใช้จ่าย/เงิน/WHT ในใบเดียว ไม่ผ่านเจ้าหนี้) — **ไม่สมมาตรกับฝั่งขาย** |
| RT ขายสด | 1 | RV ตรงเข้ารายได้ |
| DR / DP + ชำระ | 1 | RV / PV |
| CN | 1 | Dr รายได้เดิม / Cr ลูกหนี้ |
| IR | 1 | UV: Dr 212305 / Cr 212101 |
| BN, QO, PO | 0 | |

### 3.2 WHT: PEAK เลือกบัญชี ภ.ง.ด. จาก **ประเภทผู้ติดต่อ** อัตโนมัติ
| contact.type | บัญชี | แบบ |
|---|---|---|
| 2 บริษัทจำกัด (น่าจะรวม 1, 3, 8-11) | 215204 | ภ.ง.ด.53 |
| 5 บุคคลธรรมดา | **215201** | **ภ.ง.ด.1** |

API ไม่มี field เลือกแบบ ภ.ง.ด. → ค่าจ้างบุคคลภายนอก (ควรเป็น ภ.ง.ด.3 → 215203) ถูกลง ภ.ง.ด.1 ซึ่งผิดแบบยื่น (ภ.ง.ด.1 = เงินเดือน 40(1)/(2)) ต้องแก้ใน PEAK UI
→ **ระบบเราต้องมี `wht_form` ต่อรายการ** (PND1/PND3/PND53/PND54) ไม่พึ่ง contact type อย่างเดียว; default: type 5 + บัญชี 530101 เงินเดือน → PND1, type 5 + อื่น → PND3, นิติบุคคล → PND53, ต่างประเทศ → PND54

### 3.3 IR ใช้ 212305 เป็นบัญชีพัก GR/IR
IR ที่สร้างโดยไม่มี GR จะ Dr 212305 (ไม่ใช่ค่าใช้จ่าย) → หมายความว่า PEAK ออกแบบให้ GR เป็นตัวรับรู้ Dr ค่าใช้จ่าย/สินค้า และ Cr 212305 (**Inferred** จากครึ่งที่เห็น ต้องยืนยันด้วย GR approve) → ใน 04 ให้ใช้ **212305** เป็น GR/IR clearing แทน 212306 ที่เสนอไว้ และระบบเราต้องเตือนถ้ามี IR ที่ไม่มี GR คู่ (ค่าใช้จ่ายจะไม่เข้า P&L)

### 3.4 ใบลดหนี้ (CN) ผ่าน API
- line ต้องอ้าง `id` ของบรรทัดต้นฉบับ (ไม่ใช่ accountCode ลอย) ไม่งั้น "Invalid Product"
- ต้องเลือก **ลดราคา** หรือ **ลดจำนวน** อย่างใดอย่างหนึ่ง: ลดราคา = `quantity: 0, price: <ส่วนลดต่อหน่วย>` → PEAK คูณด้วยจำนวนเดิมเอง (1,000 × 2 = 2,000) ; ลดจำนวน = `price: 0, quantity: <จำนวนที่คืน>` (ยังไม่ได้ทดสอบ)
- ลงบัญชี Dr บัญชีรายได้เดิมของบรรทัดนั้น (ไม่ใช่ contra) — ถ้าต้องการแยก "รับคืน/ส่วนลดจ่าย" ในงบ ต้องทำเองที่ระบบเรา (หรือยอมรับแบบต้นแบบ)
- response ของ Create/Get CN **ไม่คืน journals, id, code** (ต้อง List เพื่อหา code)

### 3.5 Void
- void ไม่ได้ถ้ามีเอกสารอ้างอิง: "Can not void because invoice is issued billingnote" ✅ ตรง 04 §0 ข้อ 5
- void เอกสารที่มี payment ผ่าน Void* ได้สำหรับ IV (void payment ให้ด้วย) แต่ **ไม่ได้สำหรับ DR/DP** ("ErrorTransactionIsHavePayment") → ต้อง voidpayment ก่อน
- voided journal: `isVoid=1`, หายจาก TB; เลข journal ไม่ถูก reuse ในรอบนี้

### 3.6 Sub-account อัตโนมัติ
PEAK ใส่ `accountSubId/Code` ให้เองใน journal: ลูกหนี้/เจ้าหนี้/มัดจำ → sub = contact ; เงินสด/ธนาคาร → sub = payment method ; ภาษี/ค่าใช้จ่าย/รายได้ → ไม่มี sub → ระบบเราทำเหมือนกัน (sub_account auto จาก contact และ payment_method)

### 3.7 เบ็ดเตล็ดที่เจอ
- `paymentMethodCode` ถูกเก็บเป็น `"TCASH "` (มีช่องว่างท้าย) → ระบบเรา trim เสมอ
- `issuedDate` ของ BN ถูกเก็บเป็น 20261108 ทั้งที่ส่ง 20261109 → timezone shift ที่ PEAK (UTC vs +7) เฉพาะ BillingNote — ระบบเราส่ง/เก็บวันที่เป็น date ล้วน ไม่แปลง timezone
- IR response มี `isCreatedTaxInvoice`, `isAllocation`, `warehouseId`, `isCanCreateCostAdjustment`, deposit currency totals → PEAK มีคลังสินค้าและ cost adjustment อยู่หลังบ้าน

### กฎ VAT ที่ค้นพบ
1. **เลขที่เอกสารแยกชุดตามใบกำกับภาษี**: ใบกำกับ → `IVT-`, `RT-`, `DRT-` ; ไม่ใช่ใบกำกับ → `IV-`, `RE-`, `DR-` (PEAK ตั้งค่า prefix แยกให้อัตโนมัติ) → ระบบเราต้องมี sequence แยก "ใบกำกับภาษี" เพราะกฎหมายบังคับเลขที่ต่อเนื่องของใบกำกับ
2. **ภาษีขาย**: isTaxInvoice=1 → 215101 ทันที ทุกประเภท (สินค้า/บริการ/มัดจำ/ขายสด) ; isTaxInvoice=0 + vatType 3 → 215102 รอเรียกเก็บ
3. **ภาษีซื้อ**: เอกสารซื้อทุกใบลง **115402** ก่อนเสมอ; เมื่อมี receivedTaxInvoice PEAK สร้าง journal ชุด **JVTX-YYYYMMnnn** (สมุดรายวันภาษี) Dr 115401 / Cr 115402 ต่อใบกำกับ 1 ใบ ลงวันที่ journalDate พร้อม description อ้างเลขใบกำกับ → รายงานภาษีซื้อดึงจาก JVTX ไม่ใช่จากเอกสาร
4. **ปัดเศษ**: VAT = round(Σ บรรทัด vatType=3 × 0.07, 2) ระดับเอกสาร ไม่ปัดรายบรรทัด
5. **taxStatus=1 (รวม VAT)**: preTax = price × 100/107, VAT = ส่วนต่าง; WHT คิดจาก preTax
6. **CN มี VAT**: Dr 215101 ลดภาษีขายเดือนที่ออก CN
7. **Journal number reuse**: หลัง void เอกสาร เลข journal และเลขเอกสารถูกนำกลับมาใช้ใหม่ได้ (SV-202611001, IV-20261100001 ถูกออกซ้ำในรอบ 2) ⚠️ ระบบเราไม่ควรทำแบบนี้สำหรับใบกำกับภาษี (เลขต้องไม่ซ้ำตามกฎสรรพากร) — PEAK reuse เฉพาะเมื่อเป็นเลขล่าสุดที่ถูก void
